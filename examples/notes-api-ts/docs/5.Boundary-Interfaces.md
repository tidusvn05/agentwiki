# System Boundary Interface Documentation

This document describes the system's external invocation interfaces, including CLI commands, API endpoints, configuration parameters, and other boundary mechanisms.

## Command Line Interface (CLI)

### src/index.ts (node src/index.ts)

**Description**: Application entry point: loads the static config object and invokes startServer(config.port) to boot the HTTP server. No CLI argument parsing exists; all startup behavior is driven by the hardcoded config in src/config.ts (declared as package.json 'main').

**Source File**: `src/index.ts, src/config.ts, package.json`

**Options**:

- `config.port`(number): optional - TCP port the server listens on, passed to startServer. Hardcoded, not a real CLI flag. (default: `8080`)
- `config.token`(string): optional - Static development bearer token used by the auth middleware to authenticate requests. (default: `dev-token (hardcoded in src/config.ts)`)
- `config.dbUrl`(string): optional - SQLite database connection URL consumed by the db client stub. (default: `sqlite URL (hardcoded in src/config.ts)`)

**Usage Examples**:

```bash
node src/index.ts
```

```bash
ts-node src/index.ts
```

## API Interfaces

### GET /notes

**Description**: Lists all notes. notesRouter.list() executes 'SELECT * FROM notes' via db.query<Note> and returns the rows. Handler registration is a no-op stub, so the route exists in intent rather than as a live HTTP binding.

**Source File**: `src/handlers/notes.ts`

**Request Format**: HTTP GET, no body

**Response Format**: JSON array of Note objects { id, body }

**Authentication**: Static token checked by checkAuth middleware against config.token

### GET /tasks

**Description**: Lists all tasks. tasksRouter.list() executes 'SELECT * FROM tasks' via db.query<Task>. Note: no tasks table exists in db/schema.sql, so this endpoint has no backing schema.

**Source File**: `src/handlers/tasks.ts`

**Request Format**: HTTP GET, no body

**Response Format**: JSON array of Task objects

**Authentication**: Static token checked by checkAuth middleware against config.token

### GET /users

**Description**: Lists all users. usersRouter.list() executes 'SELECT * FROM users' via db.query<User>. This router is NOT mounted in src/routes/index.ts and no users table exists in db/schema.sql — a wiring/schema gap.

**Source File**: `src/handlers/users.ts`

**Request Format**: HTTP GET, no body

**Response Format**: JSON array of User objects

**Authentication**: Static token checked by checkAuth middleware against config.token

## Router Routes

### /notes

## Integration Suggestions

### REST client

Consume the API over HTTP on port 8080, supplying the configured static token with each request. Only list (GET) operations exist; there are no create/update/delete endpoints.

**Example Code**:

```
curl -H "Authorization: Bearer dev-token" http://localhost:8080/notes
```

**Best Practices**:

- Send the auth token on every request; checkAuth middleware rejects unauthenticated calls.
- Treat /tasks and /users as stubs: they lack backing tables in db/schema.sql.
- Expect stubbed behavior — router.listen/use are no-ops, so a real HTTP framework (e.g. Express) must be wired in before integration.

### Configuration

Adjust runtime behavior by editing the exported config constant in src/config.ts — there is no env-var or file-based configuration loading.

**Example Code**:

```
// src/config.ts
export const config = {
  port: 8080,
  token: 'dev-token',
  dbUrl: 'sqlite://./db/notes.db'
};
```

**Best Practices**:

- Move secrets like the auth token to environment variables before any real deployment.
- Keep dbUrl in sync with the SQLite schema location in db/schema.sql.

### Database (SQLite)

The persistence boundary is the SQLite database defined by db/schema.sql (currently only the notes table: id, body). All handlers funnel through the shared db.query client in src/infra/db.ts.

**Example Code**:

```
const rows = await db.query<Note>('SELECT * FROM notes');
```

**Best Practices**:

- Add tasks and users tables to db/schema.sql before relying on those handlers.
- Implement the stubbed db client before expecting real query results.
